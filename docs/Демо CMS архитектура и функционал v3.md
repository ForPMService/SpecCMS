# Демонстрационная CMS — архитектура и функциональный объём v3

## 1. Статус документа

Документ фиксирует целевое устройство **демонстрационной системы**, которая должна показать бизнесу практически весь основной пользовательский сценарий замены Tilda.

Это **не решение о промышленной архитектуре**. После демонстрации отдельно сравниваются:

- дальнейшее развитие на Silex;
- собственная оболочка непосредственно на GrapesJS Core;
- варианты серверной части и стоимость их сопровождения.

В демо функциональность делаем широкой, а инфраструктуру — простой и одноузловой.

Приоритет требований остаётся прежним:

1. функциональные и нефункциональные требования;
2. пользовательские сценарии;
3. принятые решения проекта;
4. технические исследования и возможности выбранных продуктов.

Продукт не меняет требование только потому, что его внутренняя модель устроена иначе.

---

## 2. Что принято, а что пока является гипотезой

### Принято

- CMS строится на **Laravel + Filament**.
- Filament — административный интерфейс внутри Laravel, а не отдельный сервис.
- Визуальный редактор демо — **Silex**, внутри которого работает **GrapesJS**.
- Silex используется как готовая оболочка редактора, а не как источник истины для нашей CMS.
- Источником истины по сайтам, страницам, правам, библиотекам, истории, формам и публикации является Laravel.
- `Page` — самостоятельная сущность CMS и должна иметь собственное редакторное состояние и собственную историю.
- Редакторное состояние и опубликованный результат — разные сущности.
- `Save` и `Build` — разные операции.
- GrapesJS должен получать корректный `ProjectData`, но CMS **не обязана хранить весь сайт одним физическим JSON-файлом или одной записью**.
- Опубликованный сайт выдаётся как обычная статика и не зависит от доступности Silex.
- Библиотечный элемент/компонент при размещении создаёт независимый экземпляр.
- Silex Symbols не используются как основа нашей библиотеки, потому что их штатная семантика — связанные экземпляры.
- Artifact после сборки неизменяем.
- Preview, Demo и Live ссылаются на конкретные собранные версии/релизы, а не на постоянно перезаписываемый каталог.
- Публикация одной страницы и публикация сайта — разные команды.
- Формы и внутренние iframe-виджеты после публикации могут обращаться к Laravel API.
- После демо Silex не считается победителем автоматически: проводится отдельное сравнение Silex и собственной оболочки над GrapesJS Core.

### Рабочая гипотеза хранения редакторного состояния

CMS хранит редакторные данные **раздельно**:

```text
Site
├── SiteSharedEditorState
│   ├── общие стили / переменные / шрифты
│   ├── общие настройки редактора
│   ├── общие editor metadata
│   └── другие действительно site-scoped данные
│
├── Page A
│   └── PageEditorState
│       ├── GrapesJS page id
│       ├── component tree
│       ├── page styles
│       └── page editor metadata
│
├── Page B
│   └── PageEditorState
│
└── Page C
    └── PageEditorState
```

На границе с GrapesJS интеграционный слой собирает из этих частей единый `ProjectData`:

```text
PageEditorState A ─┐
PageEditorState B ─┼──► adapter ─► GrapesJS ProjectData
PageEditorState C ─┤
SiteSharedState  ──┘
```

При сохранении выполняется обратная операция: `ProjectData` разбирается на состояния страниц и общую часть сайта. Сохраняются только изменившиеся сущности/версии.

Точный состав `PageEditorState` и `SiteSharedEditorState` **не зафиксирован**. Особенно требуется практическая проверка CSS, assets, CSS variables, fonts и Silex-specific project fields.

### Пока не выбрано

- способ интеграции Laravel с Silex:
  - через штатные storage/assets/publication/hosting connectors Silex;
  - либо напрямую через GrapesJS Storage/API внутри Silex;
- точная схема разложения `ProjectData` на `PageEditorState` и `SiteSharedEditorState`;
- окончательный формат хранения `ComponentDefinition`;
- точная реализация обратного импорта HTML/CSS/JS;
- промышленный визуальный редактор после завершения демо.

# 4. Laravel — хозяин предметной модели

Laravel хранит и контролирует сущности, определённые требованиями проекта.

Концептуально:

```text
Site
Page
SiteSharedEditorState
PageEditorState
User
Role
Permission
ElementDefinition
ComponentDefinition
Asset
FormDefinition
FormSubmission
PageRevision
ComponentRevision
Artifact
SiteRelease
PublicationPointer
Redirect
AuditLog
```

Laravel знает, например:

```text
Сайт Corporate
├── Главная      /
├── О компании   /about
└── Контакты     /contacts
```

Он знает URL, дерево, видимость, SEO, права и публикационное состояние.

Laravel **не должен использовать GrapesJS JSON как собственную бизнес-модель** и в обычной работе не должен зависеть от структуры вида:

```text
components[3].components[2].traits...
```

Но JSON не абсолютно непрозрачен: для истории страницы, безопасного режима редактора содержимого и проверок импорта потребуется ограниченный договорённый слой метаданных.

Filament находится внутри Laravel:

```text
Laravel
└── Filament
```

Через Filament пользователь получает обычную часть CMS:

```text
Сайты

Компоненты
Файлы
Формы
История
Публикации

```

Filament не отвечает за визуальное построение страницы.

Кнопка:

```text
Редактировать визуально
```

переводит пользователя в Silex с контекстом нужного сайта и страницы.

# 6. Site — верхняя сущность CMS

`Site` — не просто папка опубликованных файлов.

Это логическая сущность CMS:

```text
Site
├── name
├── domain
├── pages
├── page tree
├── design system
├── common resources
├── SEO defaults
├── redirects
├── editor state
├── preview pointer
├── demo pointer
└── live pointer
```

В демо должно быть минимум два реально независимых сайта, например:

```text
Corporate
├── Главная
├── О компании
└── Контакты

Product
├── Главная
├── Возможности
└── Цены
```

У каждого сайта свои:

- страницы;
- дерево;
- оформление;
- файлы;
- SEO;
- Demo;
- Live;
- опубликованный результат.

# 7. Page — отдельная сущность CMS

Страница в Laravel существует отдельно от GrapesJS Page:

```text
Page
├── id
├── site_id
├── editor_page_id
├── parent_id
├── name
├── slug
├── template
├── style_mode
├── seo
├── social_meta
├── is_visible
└── служебные данные
```

Связь:

```text
Laravel Page 102
        ↕ editor_page_id
GrapesJS Page "page-abc"
```

CMS использует `Page` для:

- дерева страниц;
- URL;
- SEO;
- скрытия;
- истории;
- экспорта;
- публикации одной страницы;
- разграничения прав.

Редактор использует GrapesJS Page для самого холста и компонентного дерева.

Физически редакторное состояние страницы хранится отдельно от других страниц:

```text
Page
├── cms fields
└── PageEditorState
    ├── editor_page_id
    ├── component tree
    ├── page styles
    └── editor metadata
```

Это позволяет отдельно версионировать, восстанавливать, экспортировать и публиковать страницу, не делая большой JSON всего сайта единицей хранения.

# 8. Рабочая модель состояния сайта

## 8.1. Не хранить сайт одним монолитным JSON

GrapesJS логически работает с `ProjectData`, в котором могут быть несколько страниц, стили, assets и другие данные проекта. Это **не означает**, что Laravel обязан хранить весь проект одной большой JSON-записью.

Рабочая модель хранения:

```text
Site
├── SiteSharedEditorState
│   ├── shared styles
│   ├── CSS variables
│   ├── fonts
│   ├── shared assets references
│   └── editor-specific shared metadata
│
├── Page 1
│   └── PageEditorState
│       ├── editor_page_id
│       ├── component tree
│       ├── page styles
│       └── page metadata
│
├── Page 2
│   └── PageEditorState
│
└── Page N
    └── PageEditorState
```

## 8.2. Что видит GrapesJS

При открытии сайта интеграционный слой собирает из хранилища структуру, понятную редактору:

```text
Laravel storage

Page 1 state ─┐
Page 2 state ─┼──► assemble ─► ProjectData
Page N state ─┤                  ├── pages[]
Shared state ─┘                  ├── styles
                                  ├── assets
                                  └── other project data
```

Далее Silex/GrapesJS работает с обычным проектом и может переключаться между страницами через Pages API.

## 8.3. Что происходит на Save

На сохранении адаптер принимает текущий `ProjectData` и раскладывает его обратно:

```text
ProjectData
    │
    ▼
decompose
    │
    ├── Page 1 state      → сохранить только если изменилось
    ├── Page 2 state      → сохранить только если изменилось
    ├── Page N state      → сохранить только если изменилось
    └── Site shared state → сохранить только если изменилось
```

Для демо достаточно определять изменение сравнением версии/хеша сериализованного состояния; промышленная оптимизация dirty tracking сейчас не требуется.

## 8.4. Почему это предпочтительнее

- страница действительно является отдельной сущностью;
- история одной страницы не требует снимка всего сайта;
- восстановление страницы не требует отката остальных страниц;
- публикация одной страницы не зависит от физического переписывания всего editor state сайта;
- размер состояния растёт по страницам, а не одним монолитом;
- проще делать экспорт/импорт страницы;
- модель Laravel не привязывается к тому, как GrapesJS сериализует весь Project.

## 8.5. Что пока неизвестно

Разделение нельзя считать окончательно доказанным, пока не проверены:

- какие `styles` реально page-scoped, а какие Silex/GrapesJS держит общими;
- как ведут себя CSS variables и fonts;
- как хранятся assets и ссылки на них;
- есть ли Silex-specific поля ProjectData, которые нельзя безопасно отделить от pages;
- корректно ли Silex работает при сборке проекта из раздельно полученных страниц;
- не ломает ли разложение/сборка autosave, publication и другие штатные механизмы Silex.

Если эти проверки не проходят, границу `PageEditorState / SiteSharedEditorState` корректируем. Возвращаться к одному большому JSON по умолчанию не требуется: сначала определяем минимальную неделимую часть состояния.

# 9. Silex — готовая оболочка редактора

Silex используется для того, чтобы не разрабатывать с нуля:

- раскладку редактора;
- панели;
- Canvas;
- DnD;
- Layers;
- Style Manager UI;
- работу со страницами;
- базовые assets;
- responsive UI;
- команды редактирования;
- часть публикационного контура.

Silex не становится хозяином наших сущностей `Site`, `Page`, `Role`, `Publication`, `Revision` и т. д.

После демо Silex оценивается отдельно как возможная промышленная оболочка.

Pages

Через эти API реализуются наши специфические функции:

- ограничения вложения;

# 11. Стык Laravel ↔ Silex — первый технический прототип

Способ интеграции **ещё не выбран**.

## Вариант A — использовать штатный контур Silex

```text
Silex
├── Storage Connector
├── Assets
├── Publication Manager
└── Hosting Connector
          │
          ▼
      наш connector
          │
          ▼
        Laravel
```

Laravel остаётся источником истины, а Silex использует свой штатный механизм хранения и публикации через наш адаптер.

Плюс варианта: меньше вмешательства во внутреннюю работу Silex.

Риск: контракт Silex может навязать лишнюю зависимость от его модели website/connector.

## Вариант B — подключиться непосредственно к GrapesJS

```text
Silex UI
└── GrapesJS
    ├── custom Storage
    ├── Pages
    ├── Blocks
    └── build adapter
             │
             ▼
           Laravel
```

Плюс варианта: более тонкая зависимость от Silex.

Риск: Silex уже связывает storage, assets, autosave и publication; обход этих механизмов может привести к фактическому переписыванию части оболочки.

## Критерий выбора

Берётся вариант, который позволяет с меньшим объёмом собственного кода:

1. собрать `ProjectData` из `PageEditorState` + `SiteSharedEditorState` и открыть сайт;
2. сохранить изменения обратно в раздельное хранилище Laravel;
3. открыть конкретную страницу по `editor_page_id`;
4. работать с assets;
5. собрать artifact;
6. не ломать штатный UX, autosave и publication Silex;
7. не привязать предметную модель CMS к внутренностям Silex.

До прототипа вариант A или B архитектурным решением не считается.

# 12. Save и Build разделены

## Save

`Save` сохраняет рабочее состояние редактора, но единицей постоянного хранения не является один монолитный JSON сайта.

Логически:

```text
Silex / GrapesJS
      │
      │ ProjectData
      ▼
Integration Adapter
      │
      ├── PageEditorState(s)
      └── SiteSharedEditorState
              │
              ▼
            Laravel
```

На первом демо допустимо получать от GrapesJS весь `ProjectData`, а в Laravel раскладывать его по страницам и общей части. Оптимизировать сетевой payload до «передавать только одну страницу» можно позже, если это потребуется.

HTML/CSS/JS для каждого обычного сохранения собирать не требуется.

## Build

Build выполняется для:

```text
Preview
Demo
Publish Page
Publish Site
Export
```

Логически:

```text
current editor state
        │
        ▼
editor/build contour
        │
        ▼
HTML + CSS + JS + assets + manifest
        │
        ▼
Laravel publication contour
```

Laravel не должен превращать GrapesJS editor state в HTML самостоятельно.

Точное место выполнения сборки — браузерный GrapesJS/Silex или штатный publication renderer Silex — определяется после прототипа интеграции. Для архитектуры важно, что CMS получает готовый artifact, а не рендерит внутреннюю модель редактора самостоятельно.

# 13. Preview / Demo / Live

## Preview

Preview показывает **текущую рабочую версию**.

Важно: Preview может включать изменения, которые пользователь ещё не сохранил отдельной командой Save.

```text
текущее состояние редактора
        │
        │ Preview
        ▼
build текущего состояния
        │
        ▼
preview artifact
```

Preview доступен авторизованному пользователю.

## Demo

Demo изменяется только явной командой:

```text
Обновить демо
```

При обновлении Demo желательно атомарно:

1. зафиксировать редакторный снимок, из которого строится версия;
2. собрать artifact;
3. перевести Demo pointer на этот artifact/release.

Demo доступен по публичной ссылке.

## Live

Live изменяется только явной публикацией:

```text
Опубликовать страницу
```

или:

```text
Опубликовать сайт
```

Редактирование, Save и Preview Live не изменяют.

# 14. Artifact неизменяем

Каждый Build создаёт новую версию результата:

```text
Artifact
├── id
├── source revision
├── files
│   ├── HTML
│   ├── CSS
│   ├── JS
│   └── assets
└── manifest
```

После создания содержимое Artifact не меняется.

Это исключает ситуацию, когда изменение рабочего состояния случайно меняет Demo или Live.

---

# 15. Site Release и manifest

Публично существует **один цельный сайт**, но это не означает, что при публикации одной страницы надо заново собирать все страницы.

Используем понятие `SiteRelease`:

```text
SiteRelease 12
├── manifest
│   ├── /            → artifact/page-home-v5
│   ├── /about       → artifact/page-about-v2
│   └── /contacts    → artifact/page-contacts-v8
└── immutable assets references
```

## Опубликовать страницу

```text
Live Release 11
├── /          → old
├── /about     → old
└── /contacts  → old

Публикуем только Contacts

Live Release 12
├── /          → reuse old
├── /about     → reuse old
└── /contacts  → NEW
```

То есть команда публикации страницы:

1. строит актуальную версию выбранной страницы;
2. создаёт новый SiteRelease;
3. переиспользует остальные страницы из предыдущего Live Release;
4. заменяет только опубликованную страницу;
5. атомарно переводит `Live` на новый release.

## Опубликовать сайт

Команда публикации сайта строит текущие версии всех включённых страниц и создаёт новый целостный SiteRelease.

## Скрыть страницу

Создаётся новый Live Release, в manifest которого маршрут страницы отсутствует. Запись `Page` в CMS не удаляется.

# 16. Общие стили и page-only publish

Это критичная часть публикационной модели.

Нельзя иметь один изменяемый `global.css`, который используется всеми уже опубликованными страницами. Иначе публикация одной страницы с новым общим цветом изменит остальные Live-страницы без их публикации, что противоречит требованиям.

Поэтому зависимости опубликованной страницы должны быть **неизменяемыми и версионированными**.

Возможные реализации:

- release-scoped CSS/JS;
- page-scoped bundles;
- content-addressed immutable assets;
- комбинация этих способов.

Точный способ выбирается позже.

Обязательная семантика:

```text
изменили Design System
       │
       ├── Preview видит новое
       │
       ├── опубликовали Page A → новое получает Page A
       │
       └── Page B в Live остаётся старой до своей публикации
```

# 17. Библиотека элементов

Библиотека принадлежит Laravel.

Концептуально:

```text
ElementDefinition
├── name
├── category
├── component definition / HTML
├── CSS
├── JS
├── properties
├── dependencies
├── assets
└── placement rules
```

Пользователь может создать собственный элемент без изменения ядра.

Например:

```text
Кнопка бренда
├── HTML
├── CSS
├── JS
└── свойства
```

После сохранения элемент становится доступен в редакторе.

# 18. Библиотека компонентов

Компонент — отдельная библиотечная сущность, а не скрытая страница сайта.

Рабочая модель:

```text
ComponentDefinition
├── component tree
├── CSS
├── JS
├── properties
├── dependencies
├── assets
├── slots
├── placement rules
└── revision
```

Точный сериализованный формат `ComponentDefinition` пока не фиксируется.

Для редактирования используется тот же Silex/GrapesJS в специальном режиме:

```text
Редактировать компонент
        │
        ▼
временный одноэкранный editor project
        │
        ▼
сохранить ComponentDefinition
```

Временный Project JSON — инструмент редактирования, а не обязательный постоянный формат хранения компонента.

# 19. Независимые экземпляры

При размещении библиотечной заготовки на странице создаётся независимая копия:

```text
ComponentDefinition v1
       │
       ├── вставить → Instance A
       └── вставить → Instance B
```

После изменения библиотеки:

```text
ComponentDefinition v2

Instance A → не меняется
Instance B → не меняется
новая вставка → получает v2
```

Для этого библиотечные определения регистрируются как Blocks / Component definitions, а не как связанные Symbols.

# 20. Области вложения

Компонент может иметь одну или несколько областей вложения:

```text
Hero
├── ContentSlot
│   ├── Heading
│   ├── Text
│   └── Button
└── MediaSlot
    └── Image
```

Для области можно задавать:

- допустимые типы объектов;
- порядок;
- возможность нескольких дочерних объектов;
- запрет вложения неподходящих элементов.

Несколько именованных областей — отдельный технический прототип, так как готовая семантика нашего `Slot` не подтверждена штатной моделью Silex.

# 21. Система оформления

На уровне Site:

```text
DesignSystem
├── colors
├── fonts
├── variables
└── global CSS
```

Страница имеет режим:

```text
1. Общий
2. Общий + переопределения
3. Изолированный
```

Экземпляр имеет локальные стили.

Логический каскад:

```text
Site
 ↓
Page
 ↓
Element / Component
 ↓
Local override
```

Silex/GrapesJS предоставляет CSS variables, Style Manager и CSS model, но правила трёх режимов и публикационная семантика являются нашей надстройкой.

# 22. Права и режим редактора содержимого

В демо реализуются четыре роли:

```text
Администратор
Дизайнер-верстальщик
Редактор содержимого
Разработчик
```

Пример разрешений:

```text
Designer
  content     = true
  structure   = true
  styles      = true
  components  = true
  code        = false
  publish     = по правам

Developer
  content     = true
  structure   = true
  styles      = true
  components  = true
  code        = true

Content editor
  text        = true
  images      = true
  structure   = false
  styles      = false
  code        = false
```

Недостаточно просто скрыть кнопки Silex.

Компонент/элемент должен описывать, **какие именно поля являются редактируемым содержимым**. Laravel и редактор используют этот контракт для проверки допустимых операций.

Например:

```text
Hero
├── title        editable:text
├── description  editable:text
├── image        editable:image
├── layout       design-only
└── javascript   code-only
```

Таким образом запрет роли редактора содержимого не является только визуальным ограничением UI.

# 26. История

## История страницы

История должна восстанавливать одну страницу, а не откатывать весь сайт.

Концептуально:

```text
PageRevision
├── page_id
├── version
├── page_editor_state_snapshot
├── references / snapshot нужных page-scoped зависимостей
├── user_id
└── created_at
```

Восстановление:

```text
Page 102 current state
        │
        └── заменить снимком revision 7

Page 101, Page 103, ...
        └── не изменяются
```

Если конкретная страница использовала версионированные общие зависимости, revision должен хранить достаточные ссылки, чтобы восстановление было воспроизводимым.

**Проверить руками:** восстановление PageRevision должно корректно переживать сборку `ProjectData` вместе с текущими состояниями остальных страниц и текущим/нужным набором общих стилей.

## История компонента

```text
ComponentRevision
├── component_id
├── version
├── definition
├── user_id
└── created_at
```

Восстановление библиотечной заготовки не меняет уже размещённые экземпляры.

Отдельная история шаблона элемента не требуется.

# 27. Export / Import

## Export

Для выбранной страницы пользователь получает стандартное представление:

```text
page/
├── index.html
├── page.css
├── page.js
└── assets/
```

Файлы должны быть пригодны для использования вне CMS.

## Import

Поддерживаем демонстрационный round-trip:

```text
Export
  ↓
внешняя правка HTML/CSS/JS
  ↓
Import
```

Поведение:

```text
распознанная структура
      ↓
возвращается в визуальную модель

валидная, но неизвестная структура
      ↓
сохраняется как Custom HTML
```

До прототипа не фиксируется способ распознавания. Возможны:

- стабильные `data-*` маркеры;
- отдельный manifest;
- сопоставление структуры;
- комбинация подходов.

Экспорт не должен требовать наличия CMS для работы итоговой страницы.

# 32. Публичная выдача

Live обслуживается статическим веб-сервером:

```text
Browser
   │
   ▼
Nginx
   │
   ▼
immutable SiteRelease
```

Silex не участвует в запросе посетителя.

Проверка демо:

```text
1. Опубликовать сайт.
2. Остановить Silex/editor.
3. Открыть Live.

```

Laravel может оставаться доступен для:

- отправки форм;
- внутренних iframe-виджетов;
- других явно динамических функций.

Поэтому требование не формулируется как «выключили весь Laravel — всё обязано работать».

# 36. Порядок реализации

Не начинаем с большого количества CRUD-экранов Filament.

Сначала закрываем архитектурные риски.

## Что должно быть доказано до широкой CMS
Нумерация работ 0–18 только в плане реализации. Этот раздел её не задаёт.
В этом порядке, независимо от номеров в плане:

1. Воспроизводимая среда: Laravel, Filament, PostgreSQL, Silex, Nginx поднимаются отдельно, без предметной модели CMS.
2. Минимальные `Site` и `Page` в Laravel. Кнопка «Редактировать визуально» на этом шаге ещё не обязана открывать Silex.
3. Тупой HTTP-канал JSON в Laravel без Silex и без GrapesJS.
4. П0. Выбор способа интеграции: штатный контур Silex или прямой GrapesJS Storage/API. Критерий: открыть, изменить, сохранить, открыть снова, не переписывая Silex.
5. П1. Раздельное хранение `PageEditorState` и `SiteSharedEditorState`, сборка и разбор `ProjectData`. Изменение одной страницы не переписывает остальные без причины.
6. П2. Обычный жизненный цикл нескольких страниц в Silex: переключение, Undo/Redo, autosave, повторное открытие.
7. П3. История и восстановление одной страницы без отката остальных.
8. Build отделён от Save. Есть immutable Artifact, Preview и Demo.
9. Live отдаётся статикой и работает после остановки Silex.
10. П4. `SiteRelease` и `Publish Page`. Публикация одной страницы с новым общим стилем не меняет остальные Live-страницы.
11. Библиотека элементов с независимыми экземплярами.
12. П5. Библиотека компонентов, вложенность, области вложения, история заготовки без изменения уже размещённых экземпляров.
13. Полная система оформления поверх уже доказанной публикационной семантики.
14. П6. Роли и редактор содержимого: запрет не только в UI, но и через контракт полей и API.
15. П7. Один рабочий round-trip Export → внешняя правка → Import, нераспознанное уходит в Custom HTML.
16. Остальной прикладной функционал CMS: дерево, SEO, файлы, формы, iframe, редиректы, расписание, журнал.
17. Сборка бизнес-демо на двух независимых сайтах и проход пользовательских сценариев.
18. Приёмка по ФТ, НФТ и сценариям.
19. Отдельное сравнение: оставить Silex или заменить оболочкой над GrapesJS Core. Демо на Silex само по себе не выбирает промышленный редактор.

## Как читать этот список

Это перечень доказательств.  
Конкретные шаги, запреты, коммиты и задания агенту берутся из плана реализации.

Нельзя перескакивать к широкой CMS, пока не закрыты П0–П4.  
Отрицательный результат прототипа уточняет гипотезу хранения или интеграции и не подменяет требование продукта.

# 37. Обязательные ручные проверки и критические прототипы

Эти пункты нельзя закрывать только документацией. До подтверждения они остаются архитектурными гипотезами.

## П0. Интеграция Silex

**Проверить руками:** connector Silex против прямого GrapesJS Storage.

**Успех:** Laravel владеет данными, Silex работает штатно, объём glue-кода мал, autosave/assets/publication не ломаются.

**Отрицательный результат:** пересмотреть способ интеграции до разработки CMS вокруг него.

## П1. Разложение и сборка ProjectData

**Проверить руками:** можно ли физически хранить страницы отдельно и собирать из них проект для GrapesJS/Silex.

Сценарий:

```text
PageEditorState A ─┐
PageEditorState B ─┼──► assemble ProjectData ─► Silex
PageEditorState C ─┤
SiteSharedState  ──┘

изменить только B
        │
        ▼
decompose ProjectData
        │
        ├── A не меняется
        ├── B новая версия
        ├── C не меняется
        └── Shared меняется только если действительно затронут
```

**Особенно проверить:**

- `page.component`;
- `page.styles`;
- общие `styles` проекта;
- CSS variables;
- fonts;
- assets;
- идентификаторы компонентов/страниц;
- внутренние ссылки между страницами;
- Silex-specific project fields.

**Успех:** после повторной загрузки визуально и структурно получаем тот же проект.

**Отрицательный результат:** уточнить границу хранения; не переходить автоматически к монолитному JSON, пока не доказано, что конкретные данные нельзя разделить.

## П2. Работа Silex с раздельной/прогрессивной загрузкой страниц

**Проверить руками:** может ли Silex открыть проект, когда страницы добавляются/собираются отдельно, и сохранить его без побочных эффектов.

Проверить:

- Pages panel;
- переключение страниц;
- autosave;
- Undo/Redo после переключений;
- assets;
- общие стили;
- publication;
- отсутствие зависимости от Symbols (Symbols не являются нашей библиотечной моделью).

**Успех:** обычный UX Silex сохраняется.

**Отрицательный результат:** интеграционный адаптер должен собирать полный `ProjectData` до загрузки редактора, даже если физическое хранение остаётся раздельным.

## П3. Восстановление одной PageRevision

**Проверить руками:** заменить состояние только одной страницы старой версией, затем собрать проект с текущими остальными страницами.

**Успех:** восстановленная страница корректна; остальные страницы, общие стили и assets не откатываются.

**Отрицательный результат:** изменить состав снимка PageRevision и модель зависимостей страницы.

## П4. Page Publish при общих стилях

**Проверить руками:** публикация одной страницы не меняет остальные Live-страницы.

**Успех:** новый release заменяет одну страницу и её immutable dependencies.

**Отрицательный результат:** изменить стратегию CSS/JS bundling и release manifest.

## П5. Независимый библиотечный компонент

**Проверить руками:** компонент редактируется отдельно, а вставленные экземпляры остаются независимыми.

**Успех:** новая версия definition влияет только на новые вставки.

**Отрицательный результат:** компонентный слой нельзя строить выбранным способом.

## П6. Редактор содержимого

**Проверить руками:** пользователь меняет только разрешённые тексты и изображения.

**Успех:** нельзя изменить структуру, стили или код через Canvas, Layers, команды или API CMS.

**Отрицательный результат:** нужен отдельный content-edit интерфейс.

## П7. Import / Export

**Проверить руками:** поддерживаемый round-trip действительно работает.

**Успех:** распознанное остаётся визуально редактируемым, неизвестное не теряется.

**Отрицательный результат:** определить более строгий контракт импорта или дополнительные метаданные экспорта.

# 38. Решение после демонстрации

После бизнес-демо проводится отдельное техническое сравнение:

```text
Вариант 1
Laravel + Filament
       +
Silex
       +
GrapesJS

против

Вариант 2
Laravel + Filament
       +
наша оболочка
       +
GrapesJS Core
```

Сравниваются не абстрактные возможности, а фактически полученный опыт:

- сколько кода потребовалось поверх Silex;
- насколько часто пришлось обходить его внутреннюю модель;
- насколько устойчивы обновления;
- можно ли реализовать наши права;
- насколько естественно реализуются библиотеки и slots;
- стоимость собственного UI поверх GrapesJS;
- зависимость от Silex internals;
- стоимость сопровождения каждого пути.

Демо на Silex не является выбором Silex для промышленной системы.

# 39. Краткая итоговая схема

```text
Пользователь CMS
      │
      ▼
Laravel + Filament
      │
      ├── Site / Page / SEO / права / история / библиотеки
      │
      ├── PageEditorState по каждой странице
      │
      ├── SiteSharedEditorState
      │
      └── Releases / Demo / Live
      │
      ▼
Integration Adapter
      │
      ├── assemble ProjectData
      └── decompose ProjectData
      │
      ▼
Silex
└── GrapesJS
      │
      ├── визуальное редактирование
      ├── Pages / Components / Blocks / Traits / Styles
      └── Build
             │
             ▼
     immutable artifacts
             │
        SiteRelease
         /    |    \
  Preview   Demo   Live
                   │
                   ▼
                 Nginx
                   │
                   ▼
               посетитель

динамические функции опубликованной страницы:
forms / internal widgets → Laravel API
```

Главная граница архитектуры:

> **Laravel владеет жизненным циклом и бизнес-моделью сайта. Страница является самостоятельной сущностью и хранит собственное редакторное состояние. Общие редакторные данные сайта хранятся отдельно. Интеграционный слой собирает из них ProjectData для Silex/GrapesJS и разбирает его обратно после сохранения. Silex/GrapesJS владеет визуальным редактированием и формированием страницы. SiteRelease владеет опубликованным состоянием. Посетитель получает готовую статику без зависимости от визуального редактора.**

# 40. Проверенные внешние основания

На момент подготовки документа:

- GrapesJS требует использовать JSON ProjectData как persistence format; HTML/CSS не рекомендуется использовать как формат восстановления проекта. При этом место физического хранения определяет приложение, а Storage Manager позволяет реализовать свой `load/store`:  
  https://grapesjs.com/docs/modules/Storage.html
- GrapesJS Pages поддерживает несколько страниц; каждая Page имеет собственные `component` и `styles`, Page можно получать по ID и отдельно получать HTML/CSS её основного компонента:  
  https://grapesjs.com/docs/modules/Pages.html
- В актуальном исходном коде Silex storage работает с `WebsiteData`, где отдельно присутствуют `pages`, `styles`, `assets` и другие части проекта; также существует progressive loading страниц. Это подтверждает техническую возможность работать со страницами как с отдельными частями проекта, но **не доказывает нашу схему хранения — её нужно проверить на выбранной стабильной версии руками**:  
  https://github.com/silexlabs/Silex/blob/main/editor/grapesjs/storage.ts
- Последний стабильный релиз Silex на момент исследования — `v3.9.0`; перед реализацией все критические проверки выполняются именно на выбранной версии демо:  
  https://github.com/silexlabs/Silex/releases
- В актуальной архитектуре Silex существуют storage connectors, assets API и publication/hosting connectors:  
  https://github.com/silexlabs/silex-server
- GrapesJS Blocks предназначены для повторного создания component definitions:  
  https://grapesjs.com/docs/modules/Blocks.html
- Filament 5 устанавливается как panel builder внутри Laravel-приложения:  
  https://filamentphp.com/docs/5.x/introduction/installation
