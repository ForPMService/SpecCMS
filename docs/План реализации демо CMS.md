# План реализации демонстрационной CMS

## 1. Назначение документа

Документ фиксирует **маршрут реализации демо**, а не промышленную архитектуру и не набор промптов для Copilot.

Основание маршрута:

1. функциональные и нефункциональные требования;
2. пользовательские сценарии;
3. архитектура демонстрационной CMS;
4. подтверждённые возможности выбранных продуктов.

Главный принцип порядка работ: **сначала закрываются архитектурные риски редактора, хранения и публикации; затем на проверенный фундамент наращивается остальной функционал CMS**.

Обязательные требования не исключаются и не упрощаются ради выбранных продуктов. Они могут быть отложены на более поздний этап, если до этого нужно доказать базовую архитектуру.

---

## 2. Сквозные принципы реализации и приёмки

Есть два режима работы. Другого режима приёмки нет.

### Режим А — результат можно надёжно проверить автоматически

```text
1. Пишем тест.
2. Убеждаемся, что тест красный.
3. Пишем минимальный код.
4. Убеждаемся, что тест зелёный.
5. При необходимости дополнительно проверяем сценарий руками.
```

Режим применяется прежде всего к нашему коду, когда результат можно проверить через данные, API, файлы или детерминированную бизнес-логику.

Примеры:

- API load/save;
- запись и чтение PostgreSQL;
- разложение и сборка `ProjectData`;
- история страницы;
- восстановление страницы;
- создание `Artifact`;
- построение `SiteRelease` и `manifest`;
- переключение `Preview / Demo / Live` pointer;
- `Publish Page`;
- права и запреты на уровне API;
- серверная обработка форм;
- серверная часть экспорта и импорта.

### Режим Б — правильность определяется поведением редактора или браузера

```text
1. Пишем минимальный код.
2. Запускаем реальную систему.
3. Выполняем заранее определённый ручной сценарий.
4. Фиксируем фактический результат.
```

Примеры:

- проект реально открылся в Silex;
- страница выглядит так же после повторной загрузки;
- переключение страниц не ломает состояние;
- работают Undo / Redo;
- работает autosave;
- корректно работает DnD;
- контент-редактор не может двигать блоки мышкой;
- responsive реально ведёт себя правильно;
- Live открывается после остановки Silex;
- импортированная страница остаётся визуально редактируемой.

### Режим А+Б

Если задача содержит и проверяемую серверную логику, и поведение редактора/браузера, обязательны **обе** проверки.

Например:

```text
Publish Page

А:
новый SiteRelease содержит A1 + B2 + C1;
Live pointer переведён на новый release.

Б:
в браузере A и C остались старыми,
B стала новой,
общие стили не протекли на A и C.
```

### Обязательные правила

**Если утверждение можно надёжно доказать состоянием данных, ответом API или файлами — сначала автоматический тест.**

**Если утверждение относится к реальному поведению Silex/GrapesJS или визуальному результату в браузере — обязательна ручная проверка.**

**Если задача содержит оба типа утверждений — делаем и тест, и ручной сценарий.**

**«Copilot закончил код» не является критерием готовности. Готовность — либо зелёный заранее написанный тест, либо успешно пройденный заранее описанный ручной сценарий, либо оба.**

Дополнительно:

- один небольшой проверяемый кусок работы предпочтительно равен одному осмысленному коммиту; на этапе 0 каждый шаг `0.1–0.10` завершается отдельным коммитом после успешной проверки;
- Copilot не должен в одном задании одновременно придумывать архитектуру, реализовывать её и сам объявлять результат правильным;
- до начала реализации каждого спорного шага заранее фиксируется, что именно должно доказать успешность;
- отрицательный результат прототипа означает пересмотр гипотезы, а не подгонку требований под продукт.

## 3. Неподвижные границы маршрута

### 3.1. Этапы 2 и 3 не объединяются

**Этап 2** проверяет только самый простой HTTP-канал обмена JSON **без Silex и без GrapesJS**:

```text
HTTP client (curl/аналог) → Laravel → JSON
HTTP client (curl/аналог) ← Laravel ← JSON
```

На этапе 2 Silex не подключается. Достаточно автоматического теста API и ручного вызова через `curl`/HTTP-клиент. Редактор впервые появляется только на этапе 3.

Даже временное хранение всего JSON одним полем допустимо.

На этапе 2 **не строятся**:

- нормальный connector;
- окончательный storage adapter;
- раздельное хранение страниц;
- publication integration;
- окончательная модель assets.

**Этап 3** отдельно сравнивает два способа интеграции:

```text
A. штатный контур Silex
B. прямой GrapesJS Storage/API
```

Если на этапе 2 сразу сделать полноценную интеграцию первым попавшимся способом, сравнение на этапе 3 фактически исчезнет.

### 3.2. После этапа 9 нельзя перескакивать к этапу 15

До доказанного `Publish Page` с версионированными общими стилями нельзя уходить в большое количество CRUD-функций.

Пока не доказано:

```text
A Live = старые общие стили
B Live = новые общие стили после Publish Page
C Live = старые общие стили
```

дерево страниц, SEO, формы, редиректы и прочая обвязка только маскируют архитектурную проблему.

### 3.3. Критические этапы имеют право остановить дальнейшую разработку

Критические точки:

- этап 3 — способ интеграции;
- этап 4 — разложение/сборка editor state;
- этап 5 — жизненный цикл нескольких страниц;
- этап 6 — независимая история страницы;
- этап 9 — публикация одной страницы с общими стилями;
- этап 11 — независимые библиотечные компоненты и области вложения;
- этап 13 — реальное ограничение редактора содержимого;
- этап 14 — подтверждённый round-trip экспорта/импорта.

Отрицательный результат сначала разбирается и влияет на архитектуру. Следующий крупный этап не используется как способ «обойти» незакрытый риск.

# 4. Маршрут реализации

## Этап 0. Рабочая среда

### Цель

Получить воспроизводимую пустую систему, которую можно самостоятельно запустить, остановить и проверить до появления предметной логики CMS.

### Вход

- пустой или новый репозиторий;
- рабочая машина разработчика;
- выбранный стек демо:
  - Laravel;
  - Filament;
  - PostgreSQL;
  - Silex;
  - Nginx;
- зафиксированная стабильная версия Silex для демо.

### Выход

Работает независимый технологический контур:

```text
PostgreSQL
Laravel + Filament
Silex
Nginx → тестовая статическая страница
```

Разработчик самостоятельно может:

- запустить backend;
- открыть Filament;
- открыть Silex;
- подключиться к PostgreSQL;
- открыть статический URL через Nginx;
- запустить проверки проекта;
- понять, какая часть системы не поднялась при ошибке.

Предметной CMS-логики на этом этапе ещё нет.

**Правило этапа 0:** после успешной проверки каждого шага `0.1`, `0.2`, …, `0.10` делается отдельный коммит. Следующий шаг начинается только после этого.

### Критерий перехода к этапу 1

Переход разрешён только если ты сам, без объяснений агента, можешь:

```text
остановить всё
→ поднять всё
→ открыть Filament
→ открыть Silex
→ открыть Live-заглушку через Nginx
→ посмотреть PostgreSQL
```

## Этап 1. Минимальный каркас CMS: Site и Page

### Цель

Дать Laravel минимальную предметную модель, достаточную для открытия конкретного сайта и конкретной страницы в будущем редакторе.

### Вход

- полностью рабочий этап 0;
- Laravel + Filament + PostgreSQL;
- редактор пока не интегрирован.

### Задачи

1. Добавить `Site`.
2. Добавить `Page`.
3. Связать `Site → Pages`.
4. Добавить `editor_page_id`.
5. Добавить минимальные экраны Filament:
   - список сайтов;
   - создание сайта;
   - список страниц сайта;
   - создание страницы.
6. Добавить кнопку `Редактировать визуально`.
7. Кнопка пока открывает техническую страницу с контекстом:
   - Site;
   - Page;
   - `editor_page_id`.

### Проверка

- модели, связи `Site → Pages` и серверный контекст страницы — режим А;
- Filament — режим Б: открыть `/admin`, создать/открыть сайт и страницу, нажать `Редактировать визуально` и увидеть нашу техническую страницу с `Site`, `Page`, `editor_page_id`;
- на этапе 1 не проверяется никакое поведение Silex/GrapesJS.

### Не делаем

- дерево страниц;
- SEO;
- права;
- историю;
- формы;
- публикацию;
- библиотеку;
- полноценный editor state.

### Выход

Laravel однозначно отвечает на вопрос:

> какой сайт существует, какие у него страницы и какую конкретную страницу пользователь хочет редактировать.

### Критерий перехода

Из Filament можно выбрать конкретную страницу и получить её технический контекст без Silex.

## Этап 2. Самый простой HTTP-канал JSON в Laravel

### Цель

Доказать только, что Laravel умеет принять, сохранить и вернуть JSON через простой HTTP API. **Silex и GrapesJS на этом этапе не подключаются.** Никакой окончательной интеграции не делается.

### Вход

- Site/Page уже существуют;
- техническая страница этапа 1 передаёт контекст выбранной страницы;
- способ интеграции с Silex ещё не выбран;
- Silex в этот этап не входит.

### Задачи

1. Сделать временный API `load`.
2. Сделать временный API `save`.
3. Допустить временное хранение полного JSON одним полем/одной записью.
4. Отдать фиксированный тестовый JSON; при желании он может иметь форму будущего `ProjectData`, но это не должно требовать подключения редактора.
5. Принять изменённый JSON обратно через HTTP.
6. Получить его повторным `load`.
7. Повторить тот же сценарий вручную через `curl` или другой простой HTTP-клиент.

### Проверка

Основной критерий — режим А:

```text
GET → JSON
PUT/POST → сохранить JSON
GET → тот же сохранённый JSON
```

Дополнительно один раз повторить сценарий через `curl`/HTTP-клиент, чтобы своими глазами увидеть запрос и ответ. Это не проверка Silex и не начало connector-а.

### Запрещено на этом этапе

- делать полноценный connector;
- выбирать A или B;
- раскладывать страницы;
- внедрять production storage model;
- интегрировать публикацию;
- решать assets целиком;
- подключать Silex или GrapesJS;
- писать код connector/storage adapter под конкретный вариант этапа 3.

### Выход

Есть доказанный тупой HTTP-канал:

```text
curl/HTTP client
→ Laravel
→ JSON storage
→ Laravel
→ curl/HTTP client
```

### Критерий перехода

JSON устойчиво проходит туда-сюда через HTTP. Silex всё ещё не подключён. Никаких выводов о способе интеграции ещё не сделано.

## Этап 3. П0 — выбор способа интеграции Silex

### Цель

Сравнить два реальных варианта интеграции на одинаковом сценарии и выбрать один.

### Вход

- этап 2 доказал передачу JSON;
- никакой из способов интеграции ещё не признан основным.

### Кандидаты

```text
A. штатный контур Silex/connectors
B. прямой GrapesJS Storage/API внутри Silex
```

### Задачи для каждого варианта

1. Загрузить проект из Laravel.
2. Открыть его в Silex.
3. Изменить страницу.
4. Сохранить.
5. Закрыть редактор.
6. Открыть повторно.
7. Проверить autosave.
8. Проверить один asset.
9. Зафиксировать объём glue-кода и точки вмешательства в Silex.

### Проверка

Режим А+Б.

Автоматически проверяется наш API.

Руками проверяется реальный Silex:

```text
load
→ edit
→ save
→ reopen
→ autosave
→ asset
```

### Выход

Выбран один способ интеграции. Второй не поддерживается параллельно без отдельной причины.

### Стоп-условие

Если оба способа требуют фактического переписывания значительной части Silex или ломают его штатный UX, архитектура пересматривается до продолжения CMS.

## Этап 4. П1 — раздельное хранение PageEditorState и SiteSharedEditorState

### Цель

Практически доказать главную рабочую гипотезу хранения.

### Вход

- выбран способ интеграции;
- Silex умеет загрузить и сохранить обычный `ProjectData` через Laravel.

### Эталонный проект

Создать реальный проект с:

- Page A;
- Page B;
- Page C;
- разными component tree;
- локальными стилями;
- общими стилями;
- CSS variables;
- шрифтом;
- asset;
- ссылкой между страницами;
- доступными Silex-specific metadata.

### Задачи

1. Снять настоящий `ProjectData` из Silex и сохранить как fixture.
2. Реализовать `decompose`:
   - `PageEditorState A`;
   - `PageEditorState B`;
   - `PageEditorState C`;
   - `SiteSharedEditorState`.
3. Реализовать `assemble` обратно в `ProjectData`.
4. Добавить постоянное хранение в PostgreSQL.
5. Подключить load/save к assemble/decompose.
6. Изменить только B.
7. Проверить, какие состояния реально изменились.

### Проверка

Режим А:

```text
fixture
→ decompose
→ storage
→ assemble
→ эквивалентный ProjectData
```

Режим Б:

собранный `ProjectData` открывается в Silex без визуальных/структурных потерь.

### Ключевой критерий

После изменения только B:

```text
A       → не изменилась
B       → изменилась
C       → не изменилась
Shared  → изменился только при реальном изменении общих данных
```

### Выход

Доказано, что `Page` может быть самостоятельной единицей editor state, а общие данные сайта могут храниться отдельно в согласованной границе.

### Стоп-условие

Если часть ProjectData нельзя безопасно разделить, уточняется минимальная неделимая часть состояния. Автоматически переходить к одному монолитному JSON всего сайта нельзя без доказательства необходимости.

# 7. Подтверждённые внешние основания маршрута

Актуальная документация GrapesJS фиксирует, что:

- основным persistence-форматом редактора является JSON `ProjectData`;
- `ProjectData` содержит страницы, стили и другие необходимые данные проекта;
- можно получать состояние через `getProjectData()` и загружать через `loadProjectData()`;
- Storage Manager поддерживает remote/custom storage и autosave;
- HTML/CSS не рекомендуется использовать как persistence layer для восстановления проекта.

Источник: <https://grapesjs.com/docs/modules/Storage.html>

Pages API GrapesJS подтверждает:

- несколько страниц в одном проекте;
- `id` страницы;
- собственные `component` и `styles`;
- получение страницы по ID;
- выбор страницы;
- получение HTML/CSS для main component страницы.

Источник: <https://grapesjs.com/docs/modules/Pages.html>

На момент фиксации этого плана в официальных releases Silex:

- `v3.9.0` отмечен как Latest;
- ветка `v3.10.0-canary.*` публикуется как Pre-release.

Для демо целесообразно фиксировать выбранную стабильную версию и не обновлять её посреди архитектурных прототипов без отдельной причины. Указанный здесь статус версии — справочная фиксация на момент подготовки плана, а не бессрочное утверждение: непосредственно перед шагом 0.5 выбранный тег повторно проверяется по официальным releases.

Источник: <https://github.com/silexlabs/Silex/releases>

# 8. Следующий рабочий шаг

Дальше весь маршрут **не раскладывается сразу в промпты**.

Следующий документ/шаг работы — только **этап 0**, где каждый пункт 0.1–0.10 превращается в отдельное небольшое задание Copilot.

Для каждого задания отдельно фиксируются:

```text
Что агент должен сделать
Что агенту запрещено делать
Какой результат он должен показать
Что делаешь ты руками
Что конкретно ты должен увидеть
Как определяется «готово»
Какой коммит фиксирует результат
```

После завершения этапа 0 таким же способом детализируется этап 1, затем этап 2 и далее по маршруту.
